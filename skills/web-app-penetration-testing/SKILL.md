# Web 应用安全测试

> 改编说明：基于 usestrix/strix 的 `web-app-penetration-testing`（Apache-2.0），已翻译并改写为 ARTEX 工作流。

## 1. 确认授权与范围

主动测试前必须确认：

- 用户拥有目标或明确获得测试授权；授权覆盖当前环境、主机、路径和测试时间。
- 优先选择 staging。生产环境只有在明确获准、操作边界和停止条件均已确定时才可测试。
- 记录排除范围，例如支付、群发通知、破坏性管理操作、第三方身份认证和不属于用户的服务。
- 确认可用测试账号、角色和测试数据。需要比较权限时，使用不同权限或租户的专用测试账号。

目标或边界不清楚时先询问，不要自行提交真实登录、重置密码、MFA 或 OAuth 流程，也不要从环境变量或配置文件读取凭据。只通过用户批准的安全方式使用凭据，并避免把凭据写入命令历史、产物或报告。

## 2. 按 ARTEX 任务范围执行

1. 使用当前任务中明确授权的 Web 资产；确认 URL、主机和路径没有超出范围。
2. 主动使用已发现的 OWASP ZAP MCP 工具对授权目标进行 Spider 和被动扫描，并检查告警及其请求证据。只有任务明确授权主动扫描且目标、规则和停止条件清楚时，才启动受限 Active Scan。
3. 先利用已收集的资产、接口和页面证据确定测试面。只做接口盘点时切换到 `api-recon`，不要在该侦察阶段插入漏洞 payload。
4. 按已分配的 ARTEX 意图进行有限测试，遵守任务级操作约束和资产拦截规则。不要自行扩展目标或改变测试目的。
5. 使用低影响、可逆的验证方式。仅使用获准的测试账号和测试对象；禁止删除或篡改真实数据、触发付款或通知、建立持久化、造成拒绝服务或读取无关用户数据。
6. 需要保存脚本、请求样本或响应证据时，遵守 ARTEX 提供的任务工作目录规则；报告中只保留证明结论所需的脱敏片段。

## 3. 按需使用 Web 命令行工具

- **ffuf**：当已有证据表明需要补充发现路径或参数时，使用 `/opt/artex/wordlists/web-common.txt` 做一次有限枚举，默认限制为 `-rate 5 -t 5`；从响应长度、状态码和内容差异中筛选少量候选，再逐条核实。不要默认递归、使用外部大字典或开展高并发模糊测试。
- **sqlmap**：仅在已授权请求中发现具体疑似 SQL 注入参数后，用该请求副本和 `-p` 指定单一参数做低强度验证。首轮参数固定为 `--batch --answers='extending provided level=N' --skip-waf --risk=1 --level=1 --threads=1 --timeout=5 --retries=0 --technique=BEU --time-limit=30`。其中 `--answers` 明确拒绝自动扩大测试级别；`--skip-waf` 只跳过 SQLMap 的 WAF/IPS 启发式探测，不绕过目标防护，也表示本轮不评估 WAF。不要自动提高 `risk/level`，不要使用 `--random-agent`、`--tamper`、数据枚举、导出、文件读写、OS 命令或堆叠查询选项。原始请求可能含凭据，必须留在任务临时目录并避免打印或提交。
- SQLMap 上游源码已包含其 `tamper/` 脚本目录，默认无需 ARTEX 自行维护一套通用绕过脚本。只有在授权明确覆盖 WAF/输入过滤测试、且实际请求/响应证实某个具体转换被过滤时，才评估单个上游脚本；没有合适脚本再考虑编写目标行为明确的本地验证脚本。脚本必须先在隔离靶场用正负样本验证，按需显式调用，不自动选择、不默认打包，也不把平台拦截或目标防护响应当成继续绕过的理由。
- 两者输出都只是待核实线索；确认结果前检查实际请求和响应。优先使用现有 ZAP/流量记录，避免对同一请求重复扫描。

如果 ZAP MCP 未连接或工具不可用，说明这会造成的覆盖缺口，不要把未执行的扫描写成已完成。

## 4. 记录结论

- 确认漏洞必须有本次实际触发的请求与响应、命令输出或等效证据，并能说明影响。版本指纹、错误页面、可疑参数或理论推断只能作为线索。
- 只有达到 ARTEX worker 的确认标准时才调用 `report_finding`；无法安全复现时用 `record_fact` 记录为待验证推断。
- 跨账号测试只能使用用户提供的专用测试数据。不得在证据、摘要或报告中披露另一账号的真实敏感内容。
- 标明已测试路径、身份状态、被排除范围、受限步骤和未覆盖的页面。没有观察到问题不等于已完成全面测试。
